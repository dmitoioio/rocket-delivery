# 03 — Життєвий цикл замовлення

## Статус-машина

```
                       cstllife                    Rocket Delivery
        ┌──────────────────────────────┐   ┌──────────────────────────────┐

  [клієнт оформив]
         │
         ▼
   placed ──────► accepted_by_business ──────► preparing ──────► ready
         │                 │                       │              │
         │                 │                       │              │  ◄── замовлення
         │                 │                       │              │      зʼявляється
         │                 │                       │              │      в черзі
         │                 │                       │              ▼
         │                 │                       │        courier_assigned
         │                 │                       │              │
         │                 │                       │              ▼
         │                 │                       │         picked_up
         │                 │                       │              │
         │                 │                       │              ▼
         │                 │                       │          on_the_way
         │                 │                       │              │
         │                 │                       │              ▼
         │                 │                       │          delivered ✅
         │                 │                       │
         ▼                 ▼                       ▼              ▼
   cancelled_by_client   rejected_by_business   failed_delivery / returned_to_queue
```

## Ключові правила

1. **Замовлення НЕ падає курʼєру одразу після оформлення.** Спочатку заклад проходить власну статус-машину. Курʼєр бачить замовлення в черзі як «буде готово о 19:40» з countdown, але **взяти його не може** до фактичного `ready`.
2. **Перехід у `ready` робить заклад вручну** — це фізична дія людини на кухні, а не таймер. У прототипі це імітовано таймером на 12–20 секунд; у продакшені таймер замінюється кнопкою в картці бізнесу на cstllife.
3. **Перед `delivered` — обовʼязкове фото** підтвердження передачі. Без фото кнопка завершення неактивна. Це не UI-обмеження, а **серверна перевірка**: `delivered` не приймається, якщо `proof_photo_path IS NULL`.

### Код клієнта — верифікація отримувача

Фото доводить, що курʼєр десь був і щось сфотографував. Воно **не доводить**, що замовлення отримав саме той, хто його зробив. Для цього — чотиризначний код (`orders.delivery_pin`):

| Хто | Що бачить |
|---|---|
| **Клієнт** | Код на сторінці свого замовлення в cstllife — єдине місце, де він показується |
| **Курʼєр** | Порожнє поле вводу. Коду він **не знає й знати не може** |
| **Сервер** | Звіряє введене з очікуваним при завершенні доставки |
| **Адмін** | Факт використання обходу, але не сам код |

> 🔒 **Сервер не віддає очікуваний код нікому.** Якщо він приїжджає курʼєру разом із замовленням, перевірку можна прочитати в інструментах розробника й не питати клієнта взагалі — верифікація стає театром. Це був реальний дефект B41, виправлений і покритий тестами.

**Обхід коду обовʼязковий.** Клієнт забуде код, не почує, розрядиться телефон — і без обходу курʼєр застрягне під дверима з їжею. Обхід дозволений, але записується в журнал і видимий адміну. Це керований виняток, а не дірка.

**Поки що не реалізовано:** сторінки клієнта, де код показується. Вона живе на боці cstllife — етап 6 дорожньої карти. До того моменту код перевірити нема звідки, тож у демо працює обхід.
4. **Курʼєр веде статуси сам** — `picked_up` → `on_the_way` → `delivered`.
5. Курʼєр веде **не більше `max_active_orders`** замовлень одночасно (1 у MVP). Це конфігурований ліміт, а не жорстка умова в коді — інакше батчинг вимагатиме переписування (баг B29).

## Два різні поля замість одного `ready_at`

Це важливо і це джерело багів (B8). У брифі `ready_at` виконує дві різні роботи одночасно.

| Поле | Тип | Хто пише | Навіщо |
|---|---|---|---|
| `estimated_ready_at` | `timestamptz` | Заклад при `accepted_by_business` | Показати курʼєру countdown «буде готово о 19:40» і клієнту очікуваний час |
| `ready_at` | `timestamptz` | Система при переході в `ready` | **Факт.** Замовлення стає доступним у черзі. До цього моменту — `NULL` |

Умова появи в черзі: `status = 'ready' AND ready_at IS NOT NULL AND courier_id IS NULL`.

Розбіжність `ready_at − estimated_ready_at` — це метрика точності закладу. Вона йде в аналітику: заклад, який систематично каже «10 хвилин», а робить 35, змушує курʼєрів чекати і псує весь графік (баг B9).

## Часові мітки

Кожен перехід фіксується. Мінімальний набір у `orders`:

```
placed_at, accepted_by_business_at, preparing_at,
estimated_ready_at, ready_at,
courier_assigned_at, picked_up_at, on_the_way_at, delivered_at,
cancelled_at
```

**Плюс окрема append-only таблиця `order_status_events`** — хто, коли, з якого статусу в який, з якого пристрою. Часових міток у самій `orders` недостатньо: вони не відповідають на питання «хто це зробив» і їх можна перезаписати. Без журналу подій спори «я тиснув доставлено» недоказові (баг B30).

Усі мітки — `timestamptz`, зберігаються в UTC, показуються в `Europe/Kyiv`. Ніяких «наївних» дат (баг B28).

## Скасування

| Статус | Хто ініціює | Коли можливий |
|---|---|---|
| `cancelled_by_client` | Клієнт | До `picked_up`. Після — тільки через адміна |
| `rejected_by_business` | Заклад | Немає товару, закінчились інгредієнти. До `picked_up` |
| `failed_delivery` | Курʼєр | Клієнт не відкриває двері, поломка скутера, ДТП |
| `returned_to_queue` | Курʼєр або адмін | Замовлення повертається в чергу для іншого курʼєра |

Кожне скасування пише рядок у `cancellations`: код причини, вільний коментар, хто ініціював, часова мітка, `refund_needed`.

### `refund_needed` — це прапорець, а не процес

Якщо скасовується замовлення, оплачене онлайн, ставиться `refund_needed = true`. **Але сам по собі прапорець нічого не повертає клієнту.**

Потрібен окремий життєвий цикл рефанду: `pending → processing → completed | failed`, виконавець (платіжний провайдер cstllife), відповідальний і SLA. Зараз цього немає — гроші клієнта зависають без жодного таймера (баг B3). Це найшвидший спосіб отримати скаргу на старті.

### `returned_to_queue` має лічильник

Без лічильника замовлення може нескінченно ходити по колу «взяв → повернув» і висіти вічно, поки клієнт чекає. Потрібно:

- `return_count` в `orders`;
- після 2 повернень — автоматична ескалація адміну;
- курʼєр, який повернув замовлення, не бачить його в черзі наступні N хвилин.

Баг B6.

### `failed_delivery` — найменш продумана гілка

Клієнт не відкрив двері. Курʼєр стоїть із суші. Бриф не відповідає на три питання:

1. **Куди їде їжа?** Назад у заклад / утилізується / залишається курʼєру?
2. **Чи отримує курʼєр оплату?** Він відпрацював поїздку. Якщо ні — курʼєри почнуть уникати «підозрілих» адрес.
3. **Чи отримує клієнт рефанд?** Якщо так — заклад втрачає і товар, і гроші. Якщо ні — це має бути в умовах до оформлення замовлення.

Це не технічне питання, це рішення власника. Винесено в [11-open-questions.md](11-open-questions.md), Q4. Баг B5.

## SLA і watchdog-таймери

**Зараз у системі немає жодного таймауту.** Замовлення може висіти в будь-якому статусі вічно, і ніхто про це не дізнається (баг B7).

Мінімальний набір таймерів, які має ставити фонова задача (Supabase cron / Edge Function за розкладом):

| Умова | Дія |
|---|---|
| `ready` і ніхто не взяв > 15 хв | Алерт адміну + позначка «висить» у дашборді |
| `courier_assigned` без `picked_up` > 20 хв | Алерт адміну |
| `picked_up` без `delivered` > 60 хв | Алерт адміну + перевірити локацію курʼєра |
| `placed` без реакції закладу > 10 хв | Алерт закладу, потім адміну |
| `refund_needed = true` без обробки > 24 год | Алерт адміну |
| Готівка не здана > періоду звірки бізнесу | Блокування нових cash-замовлень курʼєру |

## Ідемпотентність і гонки

Два місця, де без атомарності будуть реальні збої:

**Взяття замовлення.** Двоє курʼєрів тиснуть «взяти» одночасно. Потрібен умовний `UPDATE`, а не `SELECT` + `UPDATE`:

```sql
UPDATE orders
   SET courier_id = :courier, status = 'courier_assigned',
       courier_assigned_at = now()
 WHERE id = :order_id
   AND status = 'ready'
   AND courier_id IS NULL
RETURNING id;
```

Порожній `RETURNING` = замовлення вже забрали, показати курʼєру чесне «на жаль, встиг інший». Баг B25.

**Подвійний тап.** Мобільний UI + погана мережа = дубльовані запити. Кожна дія, що змінює стан, приймає `idempotency_key` від клієнта; повтор із тим самим ключем повертає той самий результат, а не створює другу дію. Баг B24.
