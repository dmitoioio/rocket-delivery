# 02 — Архітектура

## Головний принцип

cstllife і Rocket Delivery читають і пишуть у **одну спільну базу даних** — той самий проєкт Supabase, що вже обслуговує CSTL_NEWS. Вони **не спілкуються через окреме API**.

Замовлення, статуси, локація курʼєра — це рядки у спільних таблицях, на які підписані обидва фронтенди через Supabase Realtime.

Обґрунтування й розглянуті альтернативи: [ADR-0001](adr/0001-shared-supabase-database.md).

## Схема

```
┌─────────────────────────┐         ┌─────────────────────────┐
│   cstllife (CSTL_NEWS)  │         │    Rocket Delivery      │
│   PWA, GitHub Pages     │         │    PWA, Netlify         │
├─────────────────────────┤         ├─────────────────────────┤
│ • картка бізнесу        │         │ • застосунок курʼєра    │
│ • чекаут клієнта        │         │ • адмінка «Бос»         │
│ • сторінка статусу      │         │                         │
└───────────┬─────────────┘         └───────────┬─────────────┘
            │                                   │
            │      supabase-js + Realtime       │
            └─────────────────┬─────────────────┘
                              │
                 ┌────────────▼────────────┐
                 │   Supabase (спільний)   │
                 ├─────────────────────────┤
                 │ Postgres + RLS          │
                 │ Auth (ролі)             │
                 │ Realtime (WS)           │
                 │ Storage (фото доставок) │
                 │ Edge Functions          │
                 └─────────────────────────┘
```

## Межі відповідальності

| Компонент | Володіє | Не чіпає |
|---|---|---|
| cstllife | Каталог, чекаут, статус-машина закладу до `ready`, сторінка клієнта | Черга курʼєрів, зарплати, здача готівки |
| Rocket Delivery | Черга, призначення курʼєра, статуси доставки, готівка, зарплата, адмінка | Каталог товарів, ціни товарів, контент |
| Спільне | `orders`, `businesses`, `courier_locations` — обидва читають, кожен пише свою частину | — |

Розмежування прав на запис — не домовленість між командами, а **RLS-політики на рівні колонок і рядків**. Курʼєрський клієнт фізично не може змінити склад чи ціну замовлення.

## Realtime-канали

| Канал | Публікує | Слухає |
|---|---|---|
| `orders:business=<id>` | Заклад, курʼєр | Заклад — бачить свої активні замовлення |
| `orders:queue` | Заклад (перехід у `ready`) | Усі онлайн-курʼєри — нове замовлення в черзі |
| `orders:<order_id>` | Курʼєр | Клієнт — статус свого замовлення |
| `courier_location:<order_id>` | Курʼєр | Клієнт + заклад — жива точка на карті |

> ⚠️ **Локація курʼєра йде через Realtime Broadcast, а не через `INSERT` у таблицю.** Оновлення координат кожні 5–10 секунд на кожного курʼєра — це мільйони рядків за місяць і рахунок за базу на порожньому місці. У таблиці зберігається лише **остання** позиція (`UPSERT` по `courier_id`) + опційний розріджений трек-лог із TTL. Деталі — баг B16 в [09-audit.md](09-audit.md).

## Автентифікація

Один Supabase Auth на обидва застосунки. Роль зберігається в `app_metadata` (не в `user_metadata` — користувач може редагувати `user_metadata` сам, це класичний вектор ескалації привілеїв).

```
app_metadata.role ∈ { 'client', 'business', 'courier', 'admin' }
app_metadata.business_id  -- для ролі 'business'
app_metadata.courier_id   -- для ролі 'courier'
```

RLS-політики читають роль через `auth.jwt() -> 'app_metadata' ->> 'role'`. Деталі — [05-roles-auth-rls.md](05-roles-auth-rls.md).

## Що робити на боці сервера, а не в браузері

Ці операції **не можна** довіряти клієнту — вони йдуть через Edge Functions або Postgres-функції з `security definer`:

| Операція | Чому не в браузері |
|---|---|
| Взяття замовлення курʼєром | Гонка двох курʼєрів за одне замовлення — потрібен атомарний умовний `UPDATE` (баг B25) |
| Нарахування заробітку | Курʼєр не може нараховувати собі гроші |
| Підтвердження здачі готівки | Двосторонній протокол із фіксацією розбіжності |
| Видача телефону клієнта | Перевірка «цей курʼєр призначений і замовлення активне» (баг B15) |
| Створення облікового запису курʼєра | Потрібен `service_role` |
| Розрахунок відстані й перевірка радіусу | Клієнт може підмінити координати |

## Деплой

| Застосунок | Хостинг | Гілка |
|---|---|---|
| cstllife | GitHub Pages | `main` у CSTL_NEWS |
| Rocket Delivery | Netlify | `main` у цьому репозиторії |

Після інтеграції Rocket Delivery може переїхати під той самий домен, що й cstllife (підшлях `/delivery`), щоб не було проблем із cross-origin і щоб PWA був один. Це рішення відкладене до етапу інтеграції.

## Чого в архітектурі поки немає

- **Платіжний провайдер** — невідомо, який використовує cstllife. Блокує проєктування рефандів.
- **Push-повідомлення** — без них курʼєр не дізнається про нове замовлення, не тримаючи застосунок відкритим. Це дірка в операційній моделі, не в коді. Баг B32.
- **Черга офлайн-дій** — у селі звʼязок падає, дії курʼєра губляться. Баг B23.
