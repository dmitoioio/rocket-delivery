# ADR-0002: Vanilla JS + esbuild замість фреймворку

**Статус:** Прийнято

## Контекст

Прототип написано ванільним HTML/CSS/JS в одному файлі. cstllife використовує ванільний JS, PWA і esbuild. Rocket Delivery після завершення інтегрується в cstllife.

## Рішення

**Vanilla JS + esbuild + PWA.** Модульна структура в `src/`, без фреймворку, без TypeScript-збірки. Рантайм-залежності: `@supabase/supabase-js` і `leaflet`.

## Чому

- **Той самий стек, що й у cstllife.** Це головна причина. Два застосунки мають злитися — різні стеки означають або два бандли на одній сторінці, або переписування при інтеграції.
- Прототип уже написано так. Перенесення логіки 1:1 не вимагає перекладу на іншу парадигму — а бриф прямо вимагає зберегти поведінку.
- Мінімальний бандл. Курʼєр вантажить застосунок на мобільному інтернеті в селі.
- PWA без зайвих шарів: service worker, manifest, offline — усе прямо, без обгорток фреймворку.

## Відкинуті альтернативи

**React + Vite + TypeScript.** Зручніше для складного UI, типи Supabase з коробки, велика екосистема. Але розходиться зі стеком cstllife — інтеграція в спільний фронтенд стає окремим проєктом. Для застосунку з ~11 екранів виграш від фреймворку не перекриває вартість розходження.

**Залишити один HTML-файл.** Найпростіший деплой, але файл уже великий, а попереду Supabase-клієнт, Realtime-підписки, офлайн-черга, ролі й геолокація. Один файл стане некерованим і зробить неможливим code review по частинах.

## Чим платимо

- **Ручне керування станом і DOM.** Немає реактивності — оновлення інтерфейсу пишеться руками. Ризик розсинхрону стану й DOM зростає з кількістю Realtime-підписок.
- **Немає типів.** Помилки в назвах полів Supabase ловляться в рантаймі, а не при збірці. Частково компенсується JSDoc-анотаціями й генерацією типів у коментарях.
- **Немає готових компонентів.** Степер, свайп-вкладки, модалки — усе своє. Зате повний контроль над розміром бандла й поведінкою на слабких пристроях.

## Пом'якшення

- Строга модульна структура `src/features/<role>/<screen>.js` — межі замість фреймворку.
- JSDoc на публічних функціях модулів.
- Один спільний шар доступу до даних (`src/lib/db.js`) — жодних прямих викликів Supabase з екранів. Це дає єдину точку для типів, помилок і офлайн-черги.

## Умова перегляду

Якщо кількість екранів перевищить ~25 або зʼявиться друга команда — переглянути. До того моменту вартість фреймворку вища за вигоду.
