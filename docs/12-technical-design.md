# 12 — Технічний дизайн застосунку

Як застосунок влаштований усередині: модулі, стан, дані, помилки. Це рівень між [02-architecture.md](02-architecture.md) (межі систем) і власне кодом.

Стек зафіксований у [ADR-0002](adr/0002-vanilla-js-esbuild.md): vanilla JS + esbuild, без фреймворку.

---

## 1. Чотири принципи

**1. Сервер — джерело правди, клієнт — кеш.** Будь-яке значення в інтерфейсі можна викинути й перезапитати. Немає стану, який існує тільки в браузері.

**2. Оптимістично показуємо, песимістично підтверджуємо.** Курʼєр на поганому 3G не має чекати відповіді сервера, щоб побачити реакцію. Але «показали» ≠ «зафіксували» — інтерфейс завжди чесно розрізняє ці стани.

**3. Жодних прямих викликів Supabase з екранів.** Усе через `lib/db.js`. Це єдина точка, де живуть помилки, ретраї, ідемпотентність і офлайн-черга. Без цього правила додати офлайн-режим потім буде неможливо.

**4. Мережа падає — це норма, не виняток.** Село. Кожен сценарій проєктується з питання «а якщо тут обірветься?».

## 2. Модулі та правила залежностей

```
app/        ← точка входу, роутинг, композиція
   ↓
features/   ← екрани: courier/, admin/, auth/, shared/
   ↓
lib/        ← db, realtime, geo, maps, offline, format
   ↓
Supabase
```

**Залежності йдуть тільки вниз.** `lib/` нічого не знає про екрани. `features/courier/` не імпортує `features/admin/`. Спільне — тільки через `features/shared/` і `lib/`.

Це замінює межі, які у фреймворку дає його архітектура. Порушення цього правила — єдиний спосіб перетворити застосунок на той самий один файл, тільки розкиданий по текам.

## 3. Шар даних — `lib/db.js`

Єдиний вхід до бази. Кожна функція:

- повертає `{ data, error }`, ніколи не кидає виняток назовні;
- класифікує помилку (розділ 10), а не віддає сире повідомлення Supabase;
- для дій, що змінюють стан, приймає `idempotencyKey`;
- за відсутності мережі кладе дію в офлайн-чергу і повертає `{ queued: true }`.

```js
// Читання — просте
export async function fetchQueue()            {}
export async function fetchActiveOrders()     {}
export async function fetchHistory({ page })  {}

// Дії — завжди з ключем ідемпотентності
export async function acceptOrder(orderId, { idempotencyKey }) {}
export async function advanceStatus(orderId, toStatus, { idempotencyKey }) {}
export async function completeDelivery(orderId, { photoPath, pin, idempotencyKey }) {}
export async function cancelOrder(orderId, { reasonCode, note, idempotencyKey }) {}
export async function declareCashHandoff({ businessId, amount, orderIds, idempotencyKey }) {}

// Приватні дані — тільки через RPC, ніколи прямим SELECT
export async function getOrderContact(orderId) {}
```

`getOrderContact` винесено окремо навмисно: це нагадування в самому API, що телефон і точна адреса клієнта — не звичайне поле замовлення, а привілей, який видається під умову (див. [05](05-roles-auth-rls.md), B15).

## 4. Стан застосунку

Мінімальний store без фреймворку: об'єкт + підписники.

```js
// lib/store.js
const state = {
  session: null,        // хто ми і в якій ролі
  connection: 'online', // online | offline | reconnecting
  queue: [],            // черга доступних замовлень
  active: [],           // мої активні замовлення
  pending: new Map(),   // дії, відправлені але не підтверджені
  outbox: [],           // дії, що чекають мережу
};
```

**Три правила роботи зі станом:**

1. **Мутації тільки через дії.** Ніякого `state.queue.push()` з екрана.
2. **Рендер — функція від стану.** Екран перемальовується з `state`, а не патчиться точково. Для 11 екранів це дешевше й надійніше, ніж ручна синхронізація DOM.
3. **`pending` і `outbox` — частина стану, а не деталь реалізації.** Інтерфейс має показувати «відправляється» і «чекає мережу» — це видимі стани, не службові.

## 5. Realtime

### Життєвий цикл підписки

```
вхід у роль → підписка на канали ролі
   ↓
подія → мердж у store → перемальовка
   ↓
розрив → 'reconnecting' в UI → експоненційний ретрай
   ↓
відновлення → ПОВНЕ перечитування, не догортання подій
```

### Головне правило: після реконекту — повне перечитування

Realtime **не гарантує доставку подій під час розриву**. Курʼєр у зоні без покриття пропустив три події; після відновлення сокет підключиться, але пропущене не прилетить.

Тому реконект завжди супроводжується повним `fetch` тих даних, на які підписані. Спроба «догорнути» пропущені події — типова помилка, що дає тихий розсинхрон: інтерфейс показує замовлення, якого вже немає.

### Мердж подій із локальним станом

Подія з сервера може прийти, коли локально є непідтверджена дія на той самий обʼєкт.

**Правило: сервер завжди виграє.** Якщо прийшла подія по замовленню, яке є в `pending` — застосовуємо серверну версію, локальну оптимістичну відкидаємо. Клієнт не арбітр.

### Канали

| Роль | Канали |
|---|---|
| Курʼєр | `orders:queue` (усі готові), `orders:mine:<courier_id>` |
| Адмін | `orders:all`, `couriers:status` |
| Заклад (на cstllife) | `orders:business:<id>` |

Локація курʼєра передається **Broadcast**, не через записи в таблицю (B16).

## 6. Взяття замовлення — центральний сценарій

За [ADR-0009](adr/0009-open-queue-assignment.md) конкуренція — основна механіка. Цей потік виконується частіше за будь-який інший і найчастіше — невдало.

```
Тап «взяти»
   │
   ├─► Кнопку одразу вимкнути (захист від подвійного тапу, B24)
   │
   ├─► Оптимістично: картка переходить у стан «беру...»
   │
   ├─► db.acceptOrder(id, { idempotencyKey })
   │        │
   │        └─► RPC: UPDATE ... WHERE status='ready' AND courier_id IS NULL
   │
   ├─ ✅ RETURNING не порожній → замовлення моє
   │      перехід на екран активного замовлення
   │
   ├─ ❌ RETURNING порожній → програш гонки
   │      картка зникає з анімацією, показ «встиг інший»
   │      БЕЗ модалки — курʼєр лишається в черзі й може взяти наступне
   │
   ├─ ⚠️ Ліміт активних замовлень вичерпано
   │      зрозуміле повідомлення, а не загальна помилка
   │
   ├─ ⚠️ Ліміт готівки вичерпано (для cash-замовлення)
   │      «здай готівку, щоб брати замовлення з оплатою готівкою»
   │
   └─ 📵 Немає мережі
          НЕ ставимо в чергу. Взяття замовлення — єдина дія,
          яку не можна відкласти: поки ти офлайн, його забере інший.
          Чесне «немає звʼязку, спробуй ще раз».
```

**Взяття замовлення — виняток із правила офлайн-черги.** Усі інші дії відкладаються й виконаються пізніше; ця — ні. Відкладене взяття означає, що курʼєр через 10 хвилин отримає замовлення, яке вже везе інший.

## 7. Офлайн-черга — `lib/offline.js`

### Що ставиться в чергу, а що ні

| Дія | Офлайн |
|---|---|
| Зміна статусу (`picked_up`, `on_the_way`) | ✅ У чергу |
| Завершення доставки з фото | ✅ У чергу (фото теж) |
| Скасування | ✅ У чергу |
| Заявка про здачу готівки | ✅ У чергу |
| Координати | ✅ Буфер, дописуються пачкою |
| **Взяття замовлення** | ❌ **Ніколи** — див. вище |

### Механіка

```js
// Кожен елемент черги
{
  id, type, payload,
  idempotencyKey,      // сервер розпізнає повтор
  createdAt,
  attempts,
  lastError,
}
```

- сховище — IndexedDB (переживає перезавантаження й закриття вкладки);
- відправка — при `online`, при поверненні з фону і за таймером;
- ретрай — експоненційний з джитером, максимум 5 спроб;
- після 5 невдач — елемент позначається як проблемний і **показується курʼєру явно**, а не зникає мовчки;
- **порядок збережений**: дії по одному замовленню відправляються послідовно, інакше `on_the_way` може випередити `picked_up`.

### Ідемпотентність

`idempotencyKey` генерується **в момент дії користувача**, не в момент відправки. Інакше ретрай створить новий ключ і сервер сприйме його як другу дію.

## 8. Геолокація — `lib/geo.js`

```
Курʼєр онлайн + є активне замовлення
   │
   ├─► запит дозволу (немає дозволу → онлайн недоступний, B22)
   ├─► watchPosition, інтервал 8 сек
   ├─► Wake Lock
   │      └─ ПЕРЕЗАПИТ на visibilitychange — система знімає його
   │         при переході у фон. Найчастіша помилка реалізації
   │
   ├─► фільтр: не слати, якщо зсув < 20 м
   ├─► Broadcast (живий рух) + UPSERT останньої позиції
   │
   └─ delivered / офлайн → все зупиняється, Wake Lock знімається
```

Трекінг **тільки під час активного замовлення** — це і економія батареї, і вимога приватності: роботодавець не бачить, де курʼєр о другій ночі.

Деталі обмежень iOS і батареї — [07-geolocation.md](07-geolocation.md).

## 9. Фото підтвердження

```
Камера (capture="environment")
   ↓
Стиснення в canvas → max 1280px, JPEG q=0.7, ~150–300 КБ
   ↓
Прев'ю з можливістю перезняти
   ↓
Upload у приватний бакет (офлайн → у чергу разом із дією)
   ↓
completeDelivery(orderId, { photoPath, pin })
```

**Стиснення обовʼязкове.** Оригінал із сучасного телефона — 3–5 МБ; на 3G у селі це хвилина завантаження, під час якої курʼєр стоїть під дверима.

Серверна перевірка: `delivered` не приймається без `proof_photo_path` — це інваріант БД, не перевірка в UI (B13 щодо приватності, [04](04-data-model.md) щодо інваріантів).

## 10. Класифікація помилок

Сире повідомлення Supabase користувачу не показується ніколи. Кожна помилка зводиться до одного з класів:

| Клас | Що це | Що бачить курʼєр | Ретрай |
|---|---|---|---|
| `network` | Немає звʼязку | «Немає звʼязку» + стан черги | Авто |
| `conflict` | Гонку програно, статус уже змінено | «Встиг інший» | Ні |
| `permission` | RLS відхилив | «Немає доступу» + лог адміну | Ні |
| `validation` | Немає фото, невірний PIN | Конкретна причина | Ні |
| `limit` | Ліміт активних / готівки | Що саме зробити, щоб зняти | Ні |
| `auth` | Сесія протухла / курʼєра деактивовано | Вихід на логін | Ні |
| `server` | 5xx, невідоме | «Щось пішло не так» + код для підтримки | Авто, обмежено |

`permission` логується окремо й голосно: за правильних RLS-політик курʼєр не має її отримувати взагалі. Якщо вона зʼявилась — або політика надто вузька, або хтось пробує те, чого не має.

## 11. Сесія й ролі на клієнті

- роль читається з `app_metadata` токена, **не з локального стану** — інакше її можна підмінити з консолі;
- `RoleGuard` на кожному екрані: невідповідність ролі = редирект, а не приховування кнопки;
- **деактивація курʼєра має розривати сесію** — Realtime-подія по `couriers.is_active` → примусовий вихід. Без цього звільнений курʼєр працює до закінчення токена;
- `must_change_password` блокує все, крім екрана зміни пароля (ADR-0004);
- перевірки на клієнті — це UX, не безпека. Безпека — RLS і серверні перевірки.

## 12. Продуктивність

Цільовий бюджет: **< 150 КБ gzip**, інтерактивність < 2 сек на 3G.

- Leaflet вантажиться **лениво**, тільки на екранах з картою (адмінка й активне замовлення). Це найбільша залежність — тримати її поза початковим бандлом обовʼязково.
- Історія й журнал — пагінація, а не завантаження всього.
- Черга — обмежений набір колонок через VIEW (це і приватність, і трафік).
- Service worker кешує оболонку застосунку; дані — ніколи (несвіжий статус замовлення гірший за відсутність даних).

## 13. Що тестуємо

Пріоритет за ціною помилки, а не за легкістю написання тесту.

| Рівень | Що саме |
|---|---|
| **RLS (найважливіше)** | Анонім, чужий курʼєр, чужий клієнт, чужий заклад — для кожної таблиці. Плюс Realtime анонімом |
| Інваріанти БД | `delivered` без фото відхиляється; ліміт активних; гонка дає рівно одного переможця |
| Ідемпотентність | Дубль із тим самим ключем не створює другу дію |
| Офлайн-черга | Порядок, ретрай, збереження після перезавантаження |
| Статус-машина | Заборонені переходи відхиляються |
| UI | Ключові флоу на реальному мобільному, не тільки в емуляторі |

Тест «кнопки немає в інтерфейсі» тестом безпеки не є.

## 14. Спостережуваність

Мінімум, без якого пілот неможливо аналізувати:

- **час до взяття замовлення** по зонах — головна метрика черрі-пікінгу (B35);
- кількість програних гонок на курʼєра — якщо в когось 90%, у нього проблема зі звʼязком;
- розмір офлайн-черги й вік найстарішого елемента;
- частота розривів Realtime;
- усі `permission`-помилки;
- скільки часу замовлення провело в кожному статусі.

Логи не містять телефонів, адрес і фото. Тільки ID.
