# 14 — Інтеграція з cstllife

> **Кому це.** Тому, хто веде cstllife. Тут — що саме викликати, щоб замовлення з картки бізнесу потрапляло в доставку, і що повертається назад.
>
> **Стан:** наш бік готовий і перевірений (60 перевірок проти живого Postgres). Чекає двох речей від cstllife: доступу до проєкту Supabase і одного рядка виклику в чекауті.
>
> **Це технічний довідник для нас.** Щоб передати команді cstllife — є [`FOR_CSTLLIFE_CLAUDE.md`](FOR_CSTLLIFE_CLAUDE.md): самодостатній брифінг із поясненням продукту, бізнес-моделі та причин кожного рішення, розрахований на того, хто нашого репозиторію не бачив.

---

## Що вже вирішено і чому саме так

За [ADR-0001](adr/0001-shared-supabase-database.md) обидва застосунки працюють з **однією базою**. Замовлення — це один рядок, а не дві копії в двох системах: немає розсинхрону і немає «а в них статус інший».

**Наші таблиці живуть в окремій схемі `delivery`, не в `public`** ([ADR-0011](adr/0011-separate-delivery-schema.md)). Ми ніколи не бачили схеми cstllife, і `public.orders` цілком може бути зайнятий. Окрема схема фізично не може зачепити ваші таблиці.

---

## Крок 1 — звʼязати картку бізнесу

Один рядок на заклад. `external_ref` — **ваш** ідентифікатор картки, у тому вигляді, у якому він у вас є: `uuid`, слаг, число як текст — байдуже, ми не робимо припущень.

```sql
INSERT INTO delivery.businesses
  (external_ref, name, type, address_text, lat, lng, phone,
   delivery_radius_km, working_hours)
VALUES
  ('<ВАШ_ID_КАРТКИ>', 'Суші Мар', 'sushi', 'с. Дідичі, вул. Центральна 1',
   50.7192, 25.8125, '+380XXXXXXXXX',
   15,                                   -- радіус доставки, км
   '{"1":{"from":10,"to":22},"2":{"from":10,"to":22}}'::jsonb);
```

`working_hours` — по днях тижня, `0` = неділя. Порожній `{}` означає цілодобово.

**Чому радіус і графік у нас, а не у вас:** щоб їх не можна було обійти. Замовлення о 23:00 у заклад, що працює до 22:00 (баг B34), і замовлення за 33 км при ліміті 15 (баг B10) відхиляються базою, а не «мають відхилятись» вашою формою.

## Крок 2 — оформлення замовлення

**Один виклик.** Ваш код не залежить від нашої схеми: змінюємо таблиці — ваш чекаут не ламається.

```js
const { data, error } = await supabase.rpc('place_order', {
  p_business_ref:   'ВАШ_ID_КАРТКИ',
  p_items:          [{ name: 'Філадельфія', qty: 1, price: 320 }],
  p_items_total:    320,
  p_payment_method: 'cash',        // 'cash' | 'online'
  p_client_name:    'Марія',
  p_client_phone:   '+380931234455',
  p_dest_address:   'с. Метельне, вул. Лісова 12',
  p_dest_lat:       50.7100,
  p_dest_lng:       25.8300,
  p_dest_landmark:  'зелені ворота, за магазином',
  p_dest_locality:  'с. Метельне',
  p_idempotency_key: 'checkout-<ваш_id_замовлення>',
});
```

**Що робить сервер сам:**

| Дія | Навіщо |
|---|---|
| Рахує відстань з координат і перевіряє радіус | Курʼєр на скутері фізично може не доїхати (B10) |
| Перевіряє графік закладу | B34 |
| Генерує код замовлення `RD-0412` | Курʼєр читає його вголос |
| Генерує **код підтвердження** — 4 цифри | Верифікація отримувача, якої фото не дає (B12) |
| Фіксує вартість доставки на момент замовлення | Зміна тарифу не переписує історію грошей |

**`p_dest_lat` / `p_dest_lng` обовʼязкові.** Без координат курʼєр не знайде адресу в селі без нумерації будинків, а радіус нема від чого рахувати. Потрібен піндроп на карті у вашому чекауті.

**`p_idempotency_key`** — будь-який ваш унікальний рядок. Повторний виклик із тим самим ключем поверне те саме замовлення, а не створить друге (B24). Подвійний тап на телефоні — норма, а не крайній випадок.

### Помилки

Приходять кодом `SQLSTATE`, не текстом — щоб ви могли розрізняти їх програмно.

| Код | Що сталось | Що показати клієнту |
|---|---|---|
| `RD002` `business_not_found` | Невідомий `external_ref` | Технічна помилка, замовлення не створено |
| `RD004` `out_of_radius: N км при ліміті M км` | Задалеко | «На жаль, ми не доставляємо за цією адресою» |
| `RD004` `business_closed` | Поза графіком | «Заклад зараз зачинений» |
| `RD004` `business_inactive` | Заклад вимкнений | «Заклад тимчасово не приймає замовлення» |

## Крок 3 — сторінка статусу клієнта

```js
const { data } = await supabase.rpc('client_order_status', {
  p_order_code: 'RD-0412',
  p_phone: '+380931234455',       // підтвердження, що це його замовлення
});
```

Повертає: `status`, `total`, `estimated_ready_at`, `delivered_at`, `courier_name` і **`delivery_pin`**.

**Про код підтвердження.** Це єдине місце в усій системі, де він видається. Курʼєрський застосунок не отримує його **в жодній відповіді** — саме тому перевірка чогось варта. Це баг B41: раніше сервер віддавав очікуваний код разом із замовленням, і курʼєр міг прочитати його в інструментах розробника, ніколи не питаючи клієнта. Уся верифікація отримувача була театром.

Клієнту треба сказати просто: **«Назвіть курʼєру ці 4 цифри при отриманні»**. Після `delivered` код перестає видаватись.

## Крок 4 — кухня закладу

Три виклики, які замінюють автотаймер:

```js
await supabase.rpc('business_accept_order', { p_order: id, p_minutes: 20 });
await supabase.rpc('business_mark_ready',   { p_order: id });
await supabase.rpc('business_reject_order', { p_order: id, p_reason: 'out_of_stock' });
```

**Важлива різниця, яку легко пропустити.** `estimated_ready_at` — це **прогноз**, який ставить кухня при підтвердженні. `ready_at` — це **факт**, який зʼявляється тільки від натискання «готово до забору». Замовлення потрапляє в чергу курʼєрів **аж тоді**.

Одне поле для обох значень — класичне джерело багів (B8): прогноз оновлюється, і замовлення то зʼявляється в черзі, то зникає. Тому їх два.

Відхилення онлайн-оплаченого замовлення автоматично ставить `payment_status = 'refund_needed'`. **Сам процес повернення грошей не реалізований** — платіжний провайдер cstllife нам невідомий (питання Q6). Поки що це прапорець для ручної обробки.

## Крок 5 — синхронізація

Обидва застосунки підписуються на ті самі рядки:

```js
supabase
  .channel('orders')
  .on('postgres_changes',
      { event: 'UPDATE', schema: 'delivery', table: 'orders',
        filter: `business_id=eq.${businessId}` },
      (payload) => updateUI(payload.new))
  .subscribe();
```

Заклад бачить, що курʼєр забрав; клієнт бачить «в дорозі»; адмін бачить усе. Без опитування раз на 15 секунд.

**Позиція курʼєра йде через Broadcast, а не через записи в таблицю.** `INSERT` кожні 5 секунд — це ~17 000 рядків на курʼєра за добу, тобто мільйони рядків заради даних, непотрібних через годину (B16). У таблиці лежить тільки остання точка, і вона стирається, щойно курʼєр виходить зі зміни: маршрут за зміну — це стеження, а не операційна потреба.

## Що потрібно від вас, щоб це запустити

1. **Доступ до проєкту Supabase** — URL і ключі. Без цього наш бік нема куди накотити.
2. **Ваш ідентифікатор картки бізнесу** для `external_ref`.
3. **Піндроп координат у чекауті** — якщо його ще немає, це єдина справжня зміна у вашому інтерфейсі.
4. **Підтвердження, що можна накатити міграції.** Ми створюємо **окрему схему** й не торкаємось `public`, але це ваша жива база — рішення ваше, не наше.

---

## Що ми НЕ робимо і не обіцяємо

- **Не пишемо у ваші таблиці.** Взагалі. Звʼязок — один рядок `external_ref`.
- **Не знаємо вашої схеми** і не робимо припущень про неї.
- **Не реалізуємо повернення грошей** — потрібен ваш платіжний провайдер (Q6).
- **Не надсилаємо push-повідомлення** курʼєрам — окрема робота (B32).
