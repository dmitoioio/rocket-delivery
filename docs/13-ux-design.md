# 13 — UI/UX дизайн

Візуальна мова зафіксована в [08-design-system.md](08-design-system.md). Цей документ — про поведінку: екрани, стани, взаємодії, помилки.

---

## 1. Контекст використання визначає все

Курʼєр користується застосунком **на вулиці, на сонці, однією рукою, іноді в рукавичках, стоячи біля скутера або на ходу**. Не за столом.

З цього випливає все інше:

| Обмеження | Наслідок для інтерфейсу |
|---|---|
| Одна рука, великий палець | Головна дія — внизу екрана, на всю ширину |
| Сонце, поганий контраст | Великий текст, високий контраст, ніяких сірих підписів 12px |
| Рукавички, рух | Зона натискання ≥ 48×48 px. Ніяких свайпів для критичних дій |
| Поспіх, конкуренція за замовлення | Мінімум тапів до «взяти». Жодних підтверджень там, де дія оборотна |
| Поганий звʼязок | Кожен стан має чесний вигляд «не відправлено» |
| Гроші й чужа їжа | Незворотні дії (доставлено, скасувати) — з підтвердженням |

**Головне правило:** курʼєр не має **читати** інтерфейс. Він має його впізнавати боковим зором. Колір і позиція несуть сенс раніше за текст.

## 2. Карта екранів

```
Логін
  ├─ Зміна пароля (примусово при першому вході)
  │
  ├─ КУРʼЄР ─────────── 4 вкладки, свайп
  │    ├─ Черга          доступні замовлення
  │    ├─ Активне        моє поточне (степер, карта, дії)
  │    ├─ Історія        виконані + скасовані
  │    └─ Профіль        онлайн/офлайн, готівка, заробіток
  │
  └─ АДМІН ──────────── 7 вкладок, свайп
       ├─ Дашборд       карта + активні замовлення
       ├─ Курʼєри       список, створення, деактивація
       ├─ Готівка       підтвердження здач, розбіжності
       ├─ Аналітика     по закладах і зонах
       ├─ Зарплата      відомість, виплати
       ├─ Фото          підтвердження доставок
       └─ Журнал        повний лог, усі рядки клікабельні
```

## 3. Чотири стани кожного екрана

Жоден екран не вважається готовим, поки не намальовані всі чотири. Найчастіша помилка — намалювати тільки перший.

| Стан | Вимога |
|---|---|
| **Завантаження** | Скелетон у формі майбутнього контенту, не спінер по центру. Курʼєр бачить, що саме зараз зʼявиться |
| **Порожньо** | Пояснення + що зробити. «Замовлень поки немає» + час, коли зазвичай зʼявляються |
| **Помилка** | Що сталось і що робити. Ніколи не сирий текст помилки |
| **Офлайн** | Дані з кешу + чесна плашка «немає звʼязку, показано на 14:32» |

## 4. Курʼєр — черга

Найважливіший екран. Тут курʼєр заробляє, тут відбувається конкуренція.

### Картка замовлення в черзі

```
┌────────────────────────────────────┐
│ RD-0412            🔵 Готово       │
│ Суші Мар                           │
│                                    │
│ 📍 с. Метельне            7,2 км   │
│                                    │
│ 470 ₴              +15 ₴ очікування│
│                                    │
│ ┌────────────────────────────────┐ │
│ │            ВЗЯТИ               │ │
│ └────────────────────────────────┘ │
└────────────────────────────────────┘
```

**Що показуємо:** код, заклад, населений пункт, відстань, суму, надбавку за очікування.

**Чого НЕ показуємо до взяття:**

- **спосіб оплати** — інакше готівкові замовлення систематично дискримінуються (B35);
- **точну адресу, орієнтир, телефон, імʼя клієнта** — це приватні дані, і до взяття курʼєр не має на них права (B15).

> Обидва приховування — не дрібниця UI, а рішення, зафіксовані в [ADR-0009](adr/0009-open-queue-assignment.md) і [05](05-roles-auth-rls.md). Показати платіжний метод у черзі — найпростіший спосіб зламати економіку далеких доставок.

### Замовлення, яке ще готується

```
┌────────────────────────────────────┐
│ RD-0413         🟡 Готується       │
│ Суші Мар                           │
│ Буде готово через  04:32           │
│ ┌────────────────────────────────┐ │
│ │      ▓▓▓▓▓▓▓░░░░░░░░           │ │  ← прогрес, не тільки цифри
│ └────────────────────────────────┘ │
└────────────────────────────────────┘
```

Кнопки «взяти» немає — вона зʼявляється тільки після фактичного `ready` (B8). Курʼєр бачить, що скоро буде робота, і не їде додому.

### Надбавка за очікування

Замовлення, що висить понад 10 хвилин, показує `+15 ₴` акцентним кольором і піднімається вгору списку. Це єдиний захід проти черрі-пікінгу, що працює економічно, — і він має бути **видимим**, інакше не працює взагалі.

## 5. 🔴 Програш гонки — найважливіша взаємодія в застосунку

За відкритої черги ([ADR-0009](adr/0009-open-queue-assignment.md)) курʼєр програватиме частіше, ніж вигравати. Тому UX програшу проєктується **раніше** за UX виграшу.

```
Тап «ВЗЯТИ»
   │
   ├─► кнопка миттєво → «Беру...» (вимкнена)
   │
   ├─ ✅ Виграв
   │     тактильний відгук + перехід на «Активне»
   │
   └─ ❌ Програв (частіше)
         картка згасає і зникає за 200 мс
         короткий тост унизу: «Встиг інший»
         курʼєр ЛИШАЄТЬСЯ в черзі
```

**Чого не робити:**

| Антипатерн | Чому погано |
|---|---|
| Модалка «Помилка: замовлення вже призначено» | Треба закрити модалку, щоб узяти наступне. Курʼєр програє й другу гонку |
| Червоний колір, іконка помилки | Це не помилка курʼєра. Це нормальний результат конкуренції |
| Перезавантаження всієї черги | Список стрибає, курʼєр тисне навмання |

**Правильно:** зникнення картки — вже достатній сигнал. Тост підтверджує причину. Решта черги не рухається.

Якщо курʼєр програє багато гонок поспіль — це сигнал про якість звʼязку, і він має бути видимим у метриках адміна ([12](12-technical-design.md), розділ 14), а не тільки в його роздратуванні.

## 6. Курʼєр — активне замовлення

### Степер із пунктирною трасою

```
  ●━━━━━━━●┄┄┄┄┄┄┄○┄┄┄┄┄┄┄○
Взято   Забрав   В дорозі  Доставлено
```

Пройдені сегменти суцільні, майбутні — пунктирні. Це наскрізний мотив маршруту скутера з [08](08-design-system.md).

### Компонування екрана

```
┌────────────────────────────────────┐
│ RD-0412                    470 ₴   │
│ 💵 ГОТІВКА                         │  ← після взяття показуємо
├────────────────────────────────────┤
│  ●━━━━●┄┄┄┄○┄┄┄┄○                  │
├────────────────────────────────────┤
│           [ КАРТА ]                │
├────────────────────────────────────┤
│ 📍 с. Метельне, О. Денисюка 71     │
│ 🚩 зелені ворота, за магазином     │  ← орієнтир нарівні з адресою
│                                    │
│ 👤 Оксана     📞 [ Подзвонити ]    │
├────────────────────────────────────┤
│ ┌────────────────────────────────┐ │
│ │       ЗАБРАВ У ЗАКЛАДІ         │ │  ← одна головна дія
│ └────────────────────────────────┘ │
│         Скасувати замовлення       │  ← текстом, не кнопкою
└────────────────────────────────────┘
```

**Орієнтир показується нарівні з адресою, не дрібним шрифтом під нею.** У селах без нумерації будинків «зелені ворота, за магазином» — це і є адреса, а рядок вулиці часто марний.

**Готівка позначається великим акцентом.** Курʼєр має знати, що з нього чекають гроші, ще до дверей.

**Одна головна дія на екран.** Скасування — текстовим посиланням: воно можливе, але не рівноцінне.

## 7. Завершення доставки

Найвідповідальніший момент: гроші, чужа їжа, доказ.

```
Тап «ДОСТАВЛЕНО»
   │
   ├─ 1. ФОТО (обовʼязково)
   │      камера одразу, без проміжного екрана
   │      прев'ю → «Перезняти» / «Далі»
   │      стиснення непомітне для курʼєра
   │
   ├─ 2. PIN від клієнта (4 цифри)
   │      великі цифри, цифрова клавіатура
   │      «Клієнт не памʼятає код» → обхід із позначкою в журналі
   │
   ├─ 3. ГОТІВКА (тільки якщо cash)
   │      «Отримано 470 ₴?»  [Так] [Проблема]
   │
   └─ 4. Підтвердження
          ✅ + сума заробітку + «до здачі: 1 250 ₴»
```

**Чому саме такий порядок:** фото першим, бо це найдовша дія й воно має статись, поки курʼєр ще біля клієнта. PIN другим — це верифікація, вона безглузда після того, як курʼєр поїхав.

**Кнопка «Далі» неактивна без фото** — і це дублюється серверною перевіркою. UI тут зручність, інваріант — у базі.

**Обхід PIN існує обовʼязково.** Клієнт забуде код, і без обходу курʼєр застрягне під дверима з їжею. Обхід фіксується в журналі — це не дірка, це керований виняток.

## 8. Скасування

```
«Скасувати замовлення»
   ↓
Причина — великі зрозумілі варіанти, не випадайка:

  ┌──────────────────────────────┐
  │ 🚪  Клієнт не відкриває      │
  ├──────────────────────────────┤
  │ 📵  Клієнт не відповідає     │
  ├──────────────────────────────┤
  │ 🛵  Проблема зі скутером     │
  ├──────────────────────────────┤
  │ ↩️  Повернути в чергу        │
  ├──────────────────────────────┤
  │ ✏️  Інше                     │
  └──────────────────────────────┘
   ↓
Підтвердження — незворотна дія
   ↓
Що робити з їжею і грошима — за політикою Q4
```

Причини — **кнопки з іконками**, не список. Курʼєр обирає в поспіху, іноді засмучений; випадайка тут не працює.

Після скасування екран **прямо каже, що робити далі** з їжею й готівкою. Це найчастіше джерело плутанини, і його не можна лишати на здогад.

## 9. Профіль курʼєра

```
┌────────────────────────────────────┐
│  ● ОНЛАЙН            [ вимкнути ]  │
├────────────────────────────────────┤
│  Сьогодні                          │
│  7 доставок              280 ₴     │
│  Цього тижня                       │
│  31 доставка           1 240 ₴     │
├────────────────────────────────────┤
│  💵 Готівка на руках               │
│  1 250 ₴ / 2 000 ₴                 │
│  ▓▓▓▓▓▓▓▓▓▓▓▓░░░░░░                │
│  ┌────────────────────────────────┐│
│  │        ЗДАТИ ГОТІВКУ           ││
│  └────────────────────────────────┘│
└────────────────────────────────────┘
```

**Ліміт готівки показується як прогрес, не як цифра.** Курʼєр має бачити наближення до блокування завчасно, а не впертись у нього в пʼятницю ввечері з повною сумкою (B2, B38).

При досягненні ліміту cash-замовлення в черзі показуються **неактивними з поясненням**, а не зникають. Курʼєр має розуміти причину, інакше вирішить, що застосунок зламався.

Заробіток — за фактом виконаних доставок ([ADR-0009](adr/0009-open-queue-assignment.md)). Незакритий борг по готівці показується тут **до** дня виплати, а не стає сюрпризом.

### Перехід в онлайн без дозволу на геолокацію

```
┌────────────────────────────────────┐
│  📍 Потрібен доступ до локації     │
│                                    │
│  Клієнт і заклад бачать, де ти     │
│  їдеш. Без цього замовлення брати  │
│  не можна.                         │
│                                    │
│  [ Дозволити ]                     │
│                                    │
│  Уже відмовив? Налаштування →      │
└────────────────────────────────────┘
```

Пояснення **перед** системним запитом, не після відмови: браузер не покаже запит удруге (B22).

## 10. Офлайн і незавершені дії

Стан звʼязку — це **постійний елемент**, не спливаюче повідомлення.

```
┌────────────────────────────────────┐
│ 📵 Немає звʼязку · 2 дії в черзі   │  ← липка смуга вгорі
└────────────────────────────────────┘
```

| Стан дії | Вигляд |
|---|---|
| Відправляється | Приглушена картка + індикатор |
| Чекає мережу | Іконка годинника + «надішлеться автоматично» |
| Не вдалось після 5 спроб | Акцентний колір + «Спробувати ще» |

**Ніколи не показуємо успіх для того, що не підтверджене сервером.** Це головне правило офлайн-UX: курʼєр натиснув «доставлено», побачив галочку, поїхав — а замовлення висить. Одного такого випадку досить, щоб курʼєр перестав довіряти застосунку (B23).

## 11. Адмінка

Інші умови: стіл, десктоп, час подумати. Тому щільніші таблиці й більше даних на екрані — але мобільна версія обовʼязкова, бо «Бос» дивитиметься з телефона.

**Дашборд** — карта Leaflet, кружечки замовлень кольором за статусом, клік → картка деталей. Поруч — лічильники: активні, висять > 15 хв, курʼєрів онлайн.

> «Курʼєрів онлайн: 0» при активних замовленнях — це **аварійний стан**, і він має виглядати відповідно (B36).

**Готівка** — черга здач на підтвердження. Розбіжність показується як окремий помітний стан із сумою, а не рядком у таблиці ([ADR-0008](adr/0008-two-sided-cash-handoff.md)).

**Курʼєри** — створення з разовим показом пароля:

```
┌────────────────────────────────────┐
│  Курʼєра створено                  │
│                                    │
│  Логін:  rd-oleh-07                │
│  Пароль: X7k2mQp9                  │
│                                    │
│  ⚠️ Пароль показується один раз.   │
│     Збережи або передай зараз.     │
│                                    │
│  [ Скопіювати ]      [ Готово ]    │
└────────────────────────────────────┘
```

Формулювання «показується один раз» — не попередження заради ввічливості, а те, як система реально працює (ADR-0004, B17).

**Журнал** — усі рядки клікабельні, модалка з повними даними. Це поведінка з прототипу, вона зберігається.

## 12. Приватність в інтерфейсі

| Дані | Видно | Коли |
|---|---|---|
| Телефон клієнта | Тільки призначеному курʼєру | Тільки поки замовлення активне |
| Точна адреса + орієнтир | Тільки призначеному курʼєру | Після взяття, до завершення |
| Спосіб оплати | Курʼєру | Після взяття (не в черзі) |
| Фото доставки | Адмін + заклад-власник | 90 днів |
| Локація курʼєра | Клієнт + заклад | Поки замовлення активне |

В історії курʼєр бачить код, суму й дату — **не телефон і не адресу**. Виконана доставка не дає довічного доступу до контактів клієнта.

## 13. Мікровзаємодії

- **Тактильний відгук** на: успішне взяття, завершення доставки, помилку. Курʼєр у рукавичках може не побачити зміну — але відчує.
- **Ніяких анімацій довше 200 мс** на критичному шляху. Швидкість тут = гроші.
- **Countdown оновлюється щосекунди**, моноширинним шрифтом — щоб цифри не стрибали.
- **Pull-to-refresh** у черзі — навіть при Realtime. Це жест довіри: курʼєр хоче переконатись сам.
- **Звук на нове замовлення** у відкритому застосунку. Частково компенсує відсутність push (B32) — але не замінює його.

---

## 14. Доступність

- Контраст ≥ 4.5:1. **Перевірити `--electric` `#45C6F0` на `--bg` `#0B1220`** — блакитний на темно-синьому легко провалює поріг для дрібного тексту.
- Стани не кодуються **тільки** кольором: статус завжди має іконку або текст.
- Мінімальна зона натискання 48×48 px.
- Підтримка системного збільшення шрифту — верстка не ламається при 200%.
- Свайп між вкладками дублюється тапом по вкладці. **Жодна функція не доступна лише свайпом** — і свайп ігнорується всередині карти (B27).
